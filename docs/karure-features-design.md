# Karure運用向け機能拡張 企画書

- 版: 1.0
- 状態: 提案(未実装)
- 対象リポジトリ: `discord-scrapbox-bot`
- 関連文書: `docs/credit-extraction-design.md`、`docs/scrapbox-rag-qa-design.md`

---

## 1. 背景・目的

本Botは現在、MV制作コレクティブ「Karure」の運営基盤(Discord + Scrapbox)のうち、**集合知・リファレンス管理**の側面を支えている(URL保存・クレジット抽出・`/ask`・`/search`・各種通知)。

一方でKarureの実運用には、Botがまだ支えていない領域がある:

1. **チャンネル構成との不一致** — KarureのDiscordは「プロジェクトごとのチャンネル + 横断的な集合知チャンネル」という構成だが、Botは単一チャンネル(`CHANNEL_ID`)しか見ていない
2. **制作進行の管理** — 商業案件を継続的に回しており、締切の把握が運営の生命線だが、Botは関与していない
3. **クレジット運用** — Direction / Sub Direction / Compositing Direction / Cinematography / Graphic Design / Illustration Direction / Illustration / 3DCG / Shooting Cooperation 等の細分化された役割でクレジット表記を組む作業が納品のたびに発生する
4. **メンバー軸の情報検索** — 「この人が関わった案件の一覧」をすぐ引く手段がない
5. **Wikiの回覧** — メンバー全員が毎日Scrapboxを見るわけではなく、蓄積された情報がDiscord側に還流していない

本書は上記に対応する5機能(A〜E)を定義する。

### 1.1 本企画で扱わないもの

- **Misoca(請求書)連携** — API認証情報の管理が重く、また金銭情報をBot経由でDiscordに流すことは、未成年メンバーが在籍するサーバーでは情報統制上のリスクがある。**Botには載せない**と明確に判断する
- 経営数値(売上・単価等)の集計・表示 — 同上の理由で対象外
- Discord外(メール・SMS等)への通知

## 2. 設計原則

既存コードベースで確立された原則を本企画でも維持する。

| ID | 原則 | 帰結 |
|---|---|---|
| P-1 | **Scrapboxを唯一の永続ストレージとする** | Botはメモリ以外の状態を持たない(Render無料プランは再起動でファイルが消える)。締切・チャンネル設定などの永続データはすべてScrapboxページに保存する。DBは導入しない |
| P-2 | **新規の環境変数を追加しない** | 設定はコード内定数か、Scrapbox上の設定ページで持つ |
| P-3 | **新規の依存ライブラリを追加しない** | `discord.py` + `requests` のみ |
| P-4 | **ロジックは同期・純粋関数で書き、テスト可能にする** | Discordオブジェクトに依存しない関数に切り出し、`unittest.mock` でテストする |
| P-5 | **失敗は戻り値で表現し、既存機能に影響を与えない** | 新機能のどの障害も、URL保存など既存動作を止めない |
| P-6 | **追加のLLMコストを発生させない** | 本企画の5機能はすべてLLM不使用(既存の `/ask` は除く) |

## 3. 機能A: 複数チャンネル対応(基盤)

> **実装済み(簡略版で確定)**: 運用者の判断により、当初案の「チャンネル登録制(§3.2〜3.3)」ではなく、**全チャンネル開放**のシンプルなモデルで実装した。
> - スラッシュコマンドとリアクション操作(📚保存/❓質問)は**サーバー内の全チャンネル**で有効
> - メッセージ監視によるURL自動保存と自動通知の宛先は従来どおり `CHANNEL_ID` のみ(案件チャンネルのクライアントブリーフ等を無差別にWiki化しない、という当初案の意図は維持)
> - これにより `/channel` コマンド・`bot設定/チャンネル` ページ・`channel_config.py` は**不要となり、実装しない**
> - 機能B(締切)の「登録元チャンネルへの通知」は、コマンドを実行したチャンネルIDをそのまま記録すればよく、登録制なしで成立する
>
> 以下の §3.2〜3.5 は当初案の記録として残す。

### 3.1 目的

Karureの「プロジェクトチャンネル + 集合知チャンネル」構成にBotを適合させる。**本機能は B〜E の前提となる基盤**である(締切通知はプロジェクトチャンネルに届いてこそ意味がある)。

### 3.2 チャンネル種別の定義(当初案・不採用)

| 種別 | 想定チャンネル | 有効な機能 |
|---|---|---|
| **home** | 既存の `CHANNEL_ID` | 全機能 + 全自動通知(新規ページ・日次配信・ヘルスチェック・週次サマリー)の宛先 |
| **knowledge** | 集合知チャンネル | メッセージ監視によるURL自動保存、リアクション保存/質問、`/save` `/ask` `/search` `/write` `/whois` |
| **project** | 各案件チャンネル | リアクション保存/質問、`/save` `/ask` `/search` `/whois` `/deadline`(URL自動保存は**しない**。案件チャンネルにはクライアントブリーフ等のURLが流れるが、それを無差別にWiki化すべきではない) |

- **A-1**: チャンネル種別ごとの機能マトリクスは上表の通りとする。未登録チャンネルではBotは一切反応しない(現状と同じ)
- **A-2**: `CHANNEL_ID` は互換のため **home** として常に有効。既存ユーザーは何も変えずに従来動作を維持できる

### 3.3 チャンネルの登録方法

- **A-3**: `/channel add mode:<knowledge|project>` — 実行したチャンネルをその種別で登録する。「サーバーの管理」権限が必要(既存 `/alias add` と同じ権限モデル)
- **A-4**: `/channel remove` — 実行したチャンネルの登録を解除する(同権限)
- **A-5**: `/channel list` — 登録済みチャンネルの一覧を表示する(権限不要)
- **A-6**: 登録情報はScrapboxの設定ページ **`bot設定/チャンネル`** に保存する(P-1)。行形式:

```
bot設定/チャンネル
 knowledge: 1234567890123456789
 project: 2345678901234567890
 project: 3456789012345678901
```

- **A-7**: Botは起動時(`on_ready`)に設定ページを読み込んでメモリにキャッシュし、`/channel add|remove` の成功時に即時更新する。Scrapbox側でページを直接編集した場合は、既存のページ一覧キャッシュと同様のTTL(5分)で再読込する
- **A-8**: 設定ページの読込に失敗した場合は **homeチャンネルのみで動作を継続**し(P-5)、日次ヘルスチェックで検出できるようにする

### 3.4 実装方針

- 新規モジュール `channel_config.py`: 設定ページのパース/シリアライズ(純粋関数) + 読み書き
- `bot.py` 各ハンドラの冒頭にある `channel_id != CHANNEL_ID` 判定を、`_channel_allows(channel_id, feature)` に置き換える(純粋関数・テスト可能)

### 3.5 障害モード

| ID | 障害 | 挙動 |
|---|---|---|
| A-FM-1 | 設定ページが存在しない | 空設定として扱う(homeのみ)。初回 `/channel add` でページが作られる |
| A-FM-2 | 設定ページの行形式が不正 | 不正行はスキップし、正しい行だけ読む |
| A-FM-3 | 設定ページ読込の通信失敗 | 前回キャッシュを使い続ける。キャッシュも無ければhomeのみ |
| A-FM-4 | `/channel add` の書込失敗 | エラーを返信し、メモリ側も更新しない(不整合を作らない) |

## 4. 機能B: 締切リマインダー

### 4.1 目的

商業案件の締切を登録し、期日が近づいたら該当チャンネルに自動通知する。運営インパクトが最も大きい機能。

### 4.2 仕様

- **B-1**: `/deadline set name:<案件名> date:<YYYY-MM-DD>` — 実行したチャンネルに紐づけて締切を登録する。project / home チャンネルで実行可能
- **B-2**: 日付は `YYYY-MM-DD` 形式のみ受け付ける。パース不能・過去日は登録を拒否し、その旨を返信する
- **B-3**: `/deadline list` — 登録中の締切を期日昇順で一覧表示する(全チャンネル分。残り日数を併記)
- **B-4**: `/deadline done name:<案件名>` — 締切を完了として削除する
- **B-5**: 締切データはScrapboxページ **`bot設定/締切`** に保存する(P-1)。行形式:

```
bot設定/締切
 2026-08-15 | MV案件X | channel:2345678901234567890
 2026-08-20 | MV案件Y | channel:3456789012345678901
```

- **B-6**: 毎日 **9:00 JST** に締切ページを読み、以下に該当する案件を**登録元チャンネル**へ通知する:
  - 期日の **3日前** / **前日** / **当日**
  - **期日超過**(超過後は毎日通知する。完了(`/deadline done`)しない限り消えない。「消すまで鳴る」ことを仕様とする)
- **B-7**: 通知先チャンネルが削除済み等で送信できない場合は、homeチャンネルに代替通知する

### 4.3 通知の重複と欠落について(明示)

- 日次タスクは `discord.ext.tasks` の `time=` 指定で1日1回発火する。**9:00時点でBotが停止していた場合、その日の通知は欠落する**(既存の日次配信・ヘルスチェックと同じ制約)。UptimeRobotによる常時起動が前提
- 再起動しても同日中に再発火はしないため、重複通知は発生しない

### 4.4 障害モード

| ID | 障害 | 挙動 |
|---|---|---|
| B-FM-1 | 締切ページ読込失敗(9:00時点) | その日の通知をスキップし、homeに「締切データを読めませんでした」を1回通知 |
| B-FM-2 | 行形式不正 | 不正行はスキップ。`/deadline list` に「解釈できない行がN件あります」と表示(黙って無視しない) |
| B-FM-3 | 同名案件の重複登録 | `/deadline set` 時に同名があれば上書き確認ではなく**拒否**し、先に `done` するよう促す(誤上書き防止) |
| B-FM-4 | 書込失敗 | エラー返信。メモリ状態は変更しない |

## 5. 機能C: クレジット表記ジェネレーター

### 5.1 目的

納品時にYouTube概要欄等へ貼るクレジットブロックを、Scrapboxの案件ページから機械的に生成する。手作業による表記ゆれ・記載漏れを防ぐ。

### 5.2 仕様

- **C-1**: `/credits page:<案件ページ名>` — 指定したScrapboxページからクレジット行(`役割: [名前]` 形式。既存のクレジット抽出機能が保存する形式と同一)を読み取り、概要欄用テキストを生成して返信する
- **C-2**: 出力はDiscordの**コードブロック**で返す(コピペで書式が崩れないため):

```
Direction : 山田太郎
3DCG      : 鈴木花子 / 佐藤次郎
Illustration : 高橋三郎
```

- **C-3**: 整形ルール:
  - Scrapboxリンク記法 `[名前]` は外してプレーンテキストにする
  - 同一役割に複数名いる場合は ` / ` 区切りで1行にまとめる
  - 役割の並び順はページ上の出現順を維持する(Karure内の慣例順はページ側で管理する)
- **C-4**: クレジット行が1つも見つからないページの場合は、その旨と「`役割: [名前]` 形式の行が対象です」という書式説明を返す
- **C-5**: LLMは使わない(P-6)。既存の保存形式を信頼して機械的にパースする

### 5.3 障害モード

| ID | 障害 | 挙動 |
|---|---|---|
| C-FM-1 | ページが存在しない | 「ページが見つかりません」+ `/search` の利用を促す |
| C-FM-2 | 通信失敗 | エラー返信 |
| C-FM-3 | クレジット行ゼロ | C-4の通り書式説明を返す |

## 6. 機能D: `/whois`(メンバーフィルモグラフィ)

### 6.1 目的

「この人が関わった案件」を即座に一覧する。アサイン検討(「最近3DCGを誰に頼んだか」)や、クレジット確認に使う。`/ask` より速く、LLMを介さないため確実。

### 6.2 仕様

- **D-1**: `/whois name:<人名>` — 以下の手順で回答する:
  1. 既存の表記ゆれマッピング(`CREDIT_MAPPING_PAGE`)で名前を正規化する(`load_alias_map` を再利用)
  2. 正規化した名前でScrapbox全文検索(`scrapbox_search.search_pages` を再利用)
  3. ヒットしたページを一覧表示。検索スニペットに `役割: [名前]` 形式の行が含まれる場合は役割を併記する
- **D-2**: 出力例(Embed):

```
山田太郎 の関連ページ (8件)
・MV案件X — Direction
・MV案件Y — 3DCG
・MV案件Z
・山田太郎 (人物ページ)
```

- **D-3**: 人物ページ(タイトル完全一致)が存在する場合は先頭に表示する
- **D-4**: 表示は最大20件。それ以上はScrapboxの検索URLへのリンクで誘導する
- **D-5**: 役割の抽出は検索スニペットからの**ベストエフォート**とする(全ページ本文を取得するとN+1リクエストになるため行わない)。スニペットに役割行が無ければタイトルのみ表示する

### 6.3 障害モード

| ID | 障害 | 挙動 |
|---|---|---|
| D-FM-1 | ヒット0件 | 「関連ページが見つかりませんでした」+ 表記ゆれ登録(`/alias add`)の案内 |
| D-FM-2 | 検索失敗(403等) | 既存 `_format_error_reply` と同一の文言 |
| D-FM-3 | alias読込失敗 | 正規化をスキップし、入力名のまま検索を続行(機能全体を止めない) |

## 7. 機能E: 週次サマリー

### 7.1 目的

1週間分のWikiの動きをDiscordに還流し、Scrapboxを毎日見ないメンバーにも集合知を届ける。

### 7.2 仕様

- **E-1**: 毎週 **月曜 9:00 JST** に、直近7日間の新規・更新ページをhomeチャンネルへ配信する
- **E-2**: データソースはScrapboxページ一覧API(`/api/pages/{project}`)の `created` / `updated` タイムスタンプ。`created` が7日以内なら「新規」、`created` は7日より前だが `updated` が7日以内なら「更新」に分類する
- **E-3**: 出力(Embed):

```
📋 今週のScrapbox (7/6〜7/12)
新規: 5件
・ページA
・ページB …
更新: 3件
・ページC …
```

- **E-4**: 各分類の表示は最大15件。超過分は件数のみ示す
- **E-5**: 新規・更新とも0件の週は配信しない(静かなチャンネルを保つ。日次ヘルスチェックと同じ思想)
- **E-6**: `bot設定/` 配下のページ(チャンネル設定・締切)と `CREDIT_MAPPING_PAGE` は集計から除外する(運用ノイズのため)

### 7.3 実装上の注意

既存の `load_existing_pages` はタイトルのリストしか返さないため、タイムスタンプ付きの取得関数を `scrapbox_search.py` に追加する(既存関数のシグネチャは変えない)。

### 7.4 障害モード

| ID | 障害 | 挙動 |
|---|---|---|
| E-FM-1 | ページ一覧取得失敗 | その週の配信をスキップ(既存日次タスクと同様、例外はcatchしてログ) |
| E-FM-2 | タイムスタンプ欠損ページ | 集計から除外 |

## 8. セキュリティ・情報統制

| 項目 | 方針 |
|---|---|
| 金銭情報 | Botは一切扱わない(§1.1)。締切機能にも金額フィールドを**設けない** |
| 権限 | チャンネル登録(`/channel add|remove`)は「サーバーの管理」権限者のみ。締切の登録・完了は全メンバー可(制作進行は現場の作業のため) |
| 未成年メンバー | 本企画の機能はすべて既存のScrapbox情報の表示・整形であり、新たな個人情報を収集しない |
| 設定ページの改ざん | `bot設定/` ページはScrapbox編集権限者なら誰でも編集できる。Karureは信頼済みメンバーのみのプロジェクトである前提に立つ(既存の表記ゆれページと同じ信頼モデル)。不正行はA-FM-2/B-FM-2で無害化される |
| プロンプトインジェクション | 本企画の5機能はLLM不使用のため該当しない |

## 9. コスト・リソース影響

| 項目 | 評価 |
|---|---|
| LLM(OpenRouter) | **追加コストゼロ**(P-6。全機能LLM不使用) |
| Scrapbox APIアクセス | `/deadline` 日次1回 + 週次1回 + コマンド実行時のみ。既存の5分ポーリングに比べ誤差 |
| メモリ | チャンネル設定・締切のキャッシュは高々数十行のテキスト。Render 512MB制約に影響なし |
| レイテンシ | 全コマンドが検索/取得1〜2回で完結。`defer()` 適用で3秒制限も問題なし |

## 10. 実装フェーズ

依存関係(B〜EはAの上に載る)と効果の大きさから、以下の順で実装する。

| フェーズ | 内容 | 根拠 |
|---|---|---|
| **1** | A(複数チャンネル対応) + D(`/whois`) | Aは全機能の土台。Dは実装が最軽量(既存関数の組合せのみ)で即日価値が出る |
| **2** | B(締切リマインダー) | 運営インパクト最大。Scrapbox永続化パターン(P-1)をここで確立する |
| **3** | E(週次サマリー) + C(クレジットジェネレーター) | どちらも独立性が高く、後回しにしてもリスクがない |

各フェーズは実装 → テスト → PR → CI → マージの既存フローに従い、フェーズごとに独立してリリース可能とする。

## 11. テスト方針

既存規約(`unittest` + `unittest.mock.patch` + `FakeResponse`、実ネットワーク禁止)に完全準拠する。

| 対象 | 主なケース |
|---|---|
| `channel_config` パース/シリアライズ | 正常 / 空 / 不正行スキップ / 種別判定(`_channel_allows`) |
| 締切パース/判定 | 日付検証(不正形式・過去日) / 残り日数計算 / 通知対象判定(3日前・前日・当日・超過) / 不正行カウント |
| クレジット整形 | 役割まとめ / リンク記法除去 / 出現順維持 / 0件時 |
| `/whois` ロジック | alias正規化経由の検索 / スニペットからの役割抽出 / 0件 / alias失敗時の続行 |
| 週次集計 | 新規/更新の分類境界(ちょうど7日) / 除外ページ / タイムスタンプ欠損 |

## 12. 受け入れ基準(全フェーズ共通)

| ID | 基準 |
|---|---|
| K-AC-1 | 既存テストが全件成功し、新機能のロジックにテストが付いている |
| K-AC-2 | `CHANNEL_ID` のみ設定した既存環境で、従来動作が完全に維持される(チャンネル未登録なら挙動不変) |
| K-AC-3 | 新規の環境変数・依存ライブラリ・LLM呼び出しがゼロである(P-2, P-3, P-6) |
| K-AC-4 | Scrapboxが読めない状態でも、既存機能(URL保存等)が動き続ける(P-5) |
| K-AC-5 | READMEに各機能の使い方と必要権限が記載されている |
