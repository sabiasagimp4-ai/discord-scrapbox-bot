# Scrapbox RAG Q&A機能 企画書

## 1. 背景・目的

現在の `discord-scrapbox-bot` は「URLを受け取ってScrapboxに**書き込む**」方向の機能が中心で、蓄積された情報を**引き出す**手段はScrapbox本体の検索に限られる。

蓄積されたページ群（映像作品のクレジット、人物、制作会社など）に対して、Discord上から自然言語で質問し、**Wikiの内容に基づいた回答**を得られるようにする。既存のOpenRouter連携（`credit_extractor.py`）を再利用し、RAG（Retrieval-Augmented Generation）構成で実装する。

**想定するユースケース:**
- 「〇〇っていうMVの監督誰だっけ」
- 「山田太郎が関わった作品を教えて」
- 「3DCGを担当してる人で最近よく見る名前は？」

素のLLMチャットではなく、**あくまで自分たちのScrapboxに書かれている事実**に基づいて答える点が価値の中心。だからこそ「検索 → 文脈注入 → 生成」のRAG構成を採る。

## 2. スコープ

### 対象（本企画）
- Discordスラッシュコマンド `/ask 質問文` による単発Q&A
- Scrapbox全文検索APIを検索バックエンドとする
- 回答に**出典ページへのリンク**を必ず添える（ハルシネーション対策）

### 対象外（将来フェーズ / 別検討）
- 会話の文脈保持（follow-up質問。フェーズ3で検討）
- 埋め込みベクトル検索（semantic search。Scrapbox純正検索で精度が足りない場合にフェーズ3で検討）
- 回答内容のScrapboxへの自動保存

## 3. 処理フロー

```
Discord: /ask "〇〇の監督は誰？"
      │
      ▼
[1] 検索クエリ生成
      質問文 → 検索キーワード
      （フェーズ1: 質問文をそのまま使用 / フェーズ2: LLMでキーワード抽出）
      │
      ▼
[2] Scrapbox全文検索
      GET /api/pages/{project}/search/query?q={keywords}
      → 上位N件のページ（タイトル + スニペット行）
      │
      ▼
[3] コンテキスト構築
      ヒットしたページの内容を整形してプロンプトに詰める
      （フェーズ1: 検索スニペットのみ / フェーズ2: 上位数件は本文全体を追加取得）
      │
      ▼
[4] LLM生成（OpenRouter）
      system: 「与えられたScrapbox抜粋のみを根拠に答えよ。
                根拠が無ければ『わからない』と答えよ」
      user:   質問文 + コンテキスト
      │
      ▼
[5] Discordにリプライ
      回答本文 + 出典ページリンク（Embed）
```

## 4. コンポーネント設計

### 4.1 新規モジュール `scrapbox_search.py`


**Scrapbox検索APIの挙動（要調査・設計前提）:**
- `GET /api/pages/{project}/search/query?q={query}` は全文検索を行い、`pages[]` にヒットしたページとマッチ箇所のスニペット行を返す
- 複数キーワードはスペース区切りでAND検索
- 日本語はScrapbox側のトークナイズに依存するため、長い質問文をそのまま投げるとヒットしないことがある → **フェーズ2でLLMによるキーワード抽出**が効いてくる

### 4.2 検索クエリ生成

| フェーズ | 方式 | メリット / デメリット |
|---|---|---|
| フェーズ1 | 質問文をそのまま検索クエリに使用 | 実装が最小 / 自然文だとヒット率が落ちる |
| フェーズ2 | LLMで質問文 → 検索キーワード列に変換してから検索 | ヒット率向上 / LLM呼び出しが1回増える（コスト・レイテンシ増） |

フェーズ1でまず体験を作り、精度が不足したらフェーズ2でキーワード抽出を挟む。

### 4.3 コンテキスト構築とトークン管理

RAGの品質とコストはここで決まる。

- 検索ヒット上位 `N` 件（初期値 5）をコンテキストに含める
- 各ページの投入テキストは先頭 `M` 文字（初期値 1000）で打ち切る
- コンテキスト全体の上限を設ける（例: 8000文字程度）。超える場合は件数を削る
- 各抜粋の先頭にページタイトルを付与し、LLMが出典を引用できるようにする

```
# ページ: 〇〇 (MV)
[https://youtu.be/...]
 Direction: [山田太郎]
 Illustration: [鈴木花子]

# ページ: 山田太郎
関わった作品:
 ...
```

### 4.4 LLM生成（OpenRouterプロンプト方針）

`credit_extractor.py` と同じ `POST https://openrouter.ai/api/v1/chat/completions` を使用。

**systemプロンプト方針（ハルシネーション抑制が最優先）:**
- 「以下のScrapbox抜粋に**書かれている情報だけ**を根拠に答える」
- 「抜粋に根拠が無い場合は推測せず『Scrapbox内に該当する情報が見つかりませんでした』と答える」
- 「回答の根拠になったページタイトルを明示する」

**モデル選定（コストの核心）:**
- 現行デフォルトの無料モデル `nvidia/nemotron-nano-9b-v2:free` は抽出タスク向けで、**文脈統合を伴う回答生成には力不足の可能性が高い**
- RAG回答用に別の環境変数 `OPENROUTER_QA_MODEL` を設け、質の高い有料モデル（例: `anthropic/claude-3.5-haiku` 等）を指定できるようにする
- 未設定時はデフォルトモデルにフォールバック（無料で試せるが品質は保証しない）

### 4.5 Discordコマンド

```python
@tree.command(name='ask', description='Scrapboxの内容に基づいて質問に答えます')
async def ask_command(interaction, question: str):
    # チャンネル制限（既存コマンドと同様 CHANNEL_ID チェック）
    await interaction.response.defer()          # 検索+LLMで数秒かかるため必須
    answer, sources = await asyncio.to_thread(run_rag_qa, question)
    # 回答本文 + 出典リンクをEmbedで返信
```

- 既存コマンド同様 `CHANNEL_ID` でチャンネルを制限
- `defer()` で「考え中」表示（検索+LLMで3秒を超えるため）
- `run_rag_qa(question)` を**同期の純粋関数**として実装し、単体テスト可能にする（`asyncio.to_thread` でオフロード）

## 5. 環境変数（追加分）

| 変数名 | 必須 | 説明 |
|---|---|---|
| `OPENROUTER_API_KEY` | 既存（Q&Aにも流用） | LLM呼び出し用 |
| `OPENROUTER_QA_MODEL` | 任意 | RAG回答生成に使うモデル。未設定なら `OPENROUTER_MODEL` にフォールバック |
| `RAG_TOP_N` | 任意 | 検索ヒット上位何件を文脈に含めるか（デフォルト5） |

`OPENROUTER_API_KEY` 未設定時は `/ask` を無効化（`/status` の表示と同様に扱う）。

## 6. エラーハンドリング方針

- 検索が0件 → LLMを呼ばずに「該当する情報が見つかりませんでした」と即返信（無駄なトークン消費を避ける）
- Scrapbox検索・LLMのいずれかが失敗 → ユーザーにエラー種別を返す（`/status` 相当のメッセージ）
- LLMタイムアウトは長め（15〜20秒）に設定。`defer()` 済みなのでDiscordの3秒制限には抵触しない
- **ハルシネーション**: 出典リンクを必ず添えることで、ユーザーが回答の裏を取れるようにする

## 7. コスト・リスク評価

「実装コストは高いが実用性も高い」機能。主なコスト要因を明示する。

| 項目 | 内容 | 対策 |
|---|---|---|
| トークンコスト | 質問ごとに数千トークンの文脈をLLMに投入。無料モデルでは品質不足、有料モデルは従量課金 | `RAG_TOP_N` と文字数上限で1回あたりのトークンを制御。まず無料モデルで検証 |
| 検索精度 | Scrapbox純正検索は日本語の自然文に弱い | フェーズ2でLLMキーワード抽出。それでも不足なら埋め込み検索（フェーズ3） |
| レイテンシ | 検索 + (本文取得) + LLM生成で数秒〜十数秒 | `defer()` で対応済み。上位件数を絞る |
| ハルシネーション | Wikiに無いことを"それっぽく"答えるリスク | systemプロンプトで厳格に制約 + 出典リンク必須 |
| 保守 | プロンプトとモデルの品質チューニングが継続的に必要 | `/ask` に相当する debug 出力（検索ヒット・投入コンテキストの可視化）を用意 |

## 8. 段階的実装計画

### フェーズ1（MVP・本企画の実装対象）
- `scrapbox_search.py`: `search_pages` / `fetch_page_body`
- `run_rag_qa(question)`: 質問文をそのまま検索 → スニペットで文脈構築 → LLM生成 → (回答, 出典)
- `/ask` コマンド
- 出典ページリンク付きのEmbed返信
- 単体テスト（検索レスポンスのモック、コンテキスト構築、0件時の分岐）

### フェーズ2（精度向上）
- LLMによる検索キーワード抽出
- 上位数件は本文全体を追加取得してコンテキスト強化
- `/ask-debug`（検索ヒットと投入コンテキストの可視化）

### フェーズ3（発展）
- 会話文脈の保持（follow-up質問）
- 埋め込みベクトル検索（Scrapbox純正検索で精度が頭打ちの場合）

## 9. 影響範囲

- 新規ファイル: `scrapbox_search.py`、`tests/test_scrapbox_search.py`
- `bot.py`: `/ask` コマンド、`run_rag_qa()` 追加。既存機能への影響なし
- `credit_extractor.py`: OpenRouter呼び出しの共通部分を切り出して再利用するか、`/ask` 側で独立実装するかは実装時に判断（現状は独立実装が影響最小）
- `requirements.txt`: 変更なし（`requests` のみ）
- README: `/ask` コマンドと新規環境変数の追記

## 10. 未決事項

- **モデル選定**: 無料モデルでどこまで実用的な回答が出るか。実装後に実データで検証が必要
- **検索クエリ**: フェーズ1の「質問文そのまま検索」で実用に足るヒット率が出るか。ダメならフェーズ2を前倒し
- OpenRouter呼び出しの共通化（`credit_extractor` とのコード重複をどう扱うか）
- コンテキスト投入時のScrapbox記法（`[...]` リンクや画像記法）をそのまま残すか、プレーン化するか
